Set Functions-scoped `RESEND_API_KEY`, `ENQUIRY_EMAIL_FROM` (a Resend-verified sender address), and `ENQUIRY_ALLOWED_ORIGIN` (the exact HTTPS production origin, without trailing slash) in Netlify. Never prefix secrets with `VITE_`. Offline tests mock delivery; verify deployed routes, rate limits, email receipt and photo attachments separately with authorized test data.

## Netlify rate-limit review

Both `netlify/functions/contact.mjs` and `solar-fit.mjs` export the same rule: `windowLimit: 5`, `windowSize: 60`, `aggregateBy: ['ip', 'domain']`, `action: 'rate_limit'`. This is valid code-based Function configuration for per-IP/domain aggregation. It is not a shared global cap across all visitors or a distributed application counter. Code-based rules are available on all plans, with plan-specific rule quotas; the current free/starter quota is two, so verify that no additional project rules consume it. Source: [Netlify rate-limiting documentation](https://docs.netlify.com/manage/security/secure-access-to-sites/rate-limiting/), reviewed 2026-10-28.

Enforcement belongs to Netlify's hosted request infrastructure, not `createEnquiryHandler` or the offline Node tests. Those tests assert exported configuration and handler behavior; they do not prove throttling. Without deploying during this task, the remaining live check is to confirm both rules were accepted, test each deployed endpoint with non-delivery test requests, observe HTTP 429 and recovery after the window, and check behavior across client IPs and domains. Ensure throttled requests do not reach the provider. Check the project's actual plan/rule quota and any additional platform rules. Origin checks and Resend idempotency are separate protections, not substitutes for rate limiting. No in-memory counter or fake local enforcement was added.
